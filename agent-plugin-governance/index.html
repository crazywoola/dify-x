01 · 先看插件拿到了什么

装上一个插件，等于放开了三类权限。

{ }

代码执行

运行依赖、命令和二进制，也能发起模型调用。

↕

数据访问

读取文件、对话、知识库、凭证和工作区上下文。

◎

网络访问

连接第三方 API、任意 URL 和其他外部服务。

治理不只是检查“装不装得上”，更要回答：它能做什么、证据在哪、出了事谁负责。

从企业视角看，插件不只是多了一个功能。它还拿到了代码执行、数据访问和网络访问三类权限。后面的治理设计，都从这三类权限往下展开。
Observed risk · 已发现的问题

第一批问题并不高深：有人把整个开发目录打进了安装包。

包里出现了开发残留和敏感文件；插件守护进程一解包，这些内容就会落到用户机器上。

.env / 环境变量与密钥 .git/ / 提交历史 .venv/ / 本地环境 *.exe / *.so 日志 / 缓存 / IDE
PACKAGE → DAEMON → TENANT
来源：飞书《Dify 插件生态治理提案》执行摘要与“风险敞口”章节；列举的是抽样中已经发现的包污染类型。
抽样包里已经出现 .env、.git、虚拟环境、日志和平台二进制。这些文件会跟着安装包落到用户机器上。这不是单个作者粗心这么简单，而是发布流程没有把风险挡在前面。

Six lenses · 一件事，六种问法

同一个插件，六个团队会问六套不同的问题。

01 / SECURITY

供应链风险

有没有密钥、二进制和漏洞依赖？运行时会做什么？

02 / LEGAL

法律责任

平台、作者和第三方各担什么责任？下架和申诉怎么走？

03 / PRODUCT

用户怎么判断

权限、数据流、签名、SBOM 和风险级别能不能看懂？

04 / ENGINEERING

规则能否落地

能否本地先检、CI 分级，并让报告直接定位问题？

05 / COMMUNITY

作者能否配合

低风险少打扰、规则能预跑、例外有说明。

06 / BUSINESS

企业能否放行

安全和采购团队有没有足够证据签字，并定期复核？

安全看供应链，法务看责任，产品要让用户看懂证据。工程和社区关心规则能不能长期执行，商业团队则要回答客户最直接的问题：这个插件能不能通过安全和采购评估。这六套问题必须放到一张桌上解决。

来源：飞书提案 §2.4 与 §3.1。法律定位需由适用法域下的专业法务最终判断。

Responsibility chain · 数据流与责任链

企业真正关心的是：数据去了哪里，最后谁负责。

01 · CUSTOMER

业务方（Controller）

决定为什么处理数据，负责内部授权和业务结果。

02 · PLATFORM

Dify 平台（Processor？）

承载执行、凭证、分发和审计；具体角色取决于部署方式。

03 · AUTHOR

插件作者（Sub-processor？）

决定具体实现和下游调用；协议与告知仍需补强。

04 · DOWNSTREAM

第三方 API

数据落在哪、保留多久、是否继续转交，都要让用户看得见。

隐私

数据类型、用途、第三方。

知识产权

权属、许可、分发权。

处置程序

通知、申辩、复议。

证据

签名、SBOM、时间戳。

来源：飞书提案 §3.2–§3.5。图中问号表示角色需按具体处理场景与合同关系认定。
这里的问号不能随便去掉，因为 GDPR 角色要结合部署方式和合同关系判断。法务至少要看清四件事：谁决定处理目的，谁实际处理数据，数据又交给了谁，出了问题如何通知、申诉和举证。
Risk proportionality · 按风险设门槛

不要一刀切：权限越大，门槛越高。

档位典型行为机器检查人工审核用户感知
L1固定 HTTPS API；不写本地文件基础门禁 + Semgrep 提示20% 抽检不额外打断
L2用户文件 / URL；上传下载与复杂解析中高危依赖阻断；警告需解释轻量人工审查展示数据去向
L3命令、SQL、SSH、浏览器、本地文件、任意 HTTP警告全部阻断；低危以上依赖阻断深度审核 + 动态测试风险提示 + 安装二次确认

低风险少打扰，高风险不靠运气。

来源：飞书提案附录 C《风险分级标准》及其嵌入表格。
插件治理不能一律从严。作者自评和机器识别取更高档，审核人仍可以上调风险级别。这样既守住安全，也不让普通贡献者承担 L3 的审核成本。
Lifecycle governance · 信任要持续

一次 CI 通过，只能说明当时没有查出问题。

01

作者提交

严格模板、.difyignore、风险自评、权限与数据声明。

02

构建

源码地址、提交 SHA、锁定依赖和安装包指纹。

03

入库门禁

密钥、二进制、依赖、SAST、插件清单和风险档位。

04

上架展示

区分官方、合作伙伴和社区，展示风险与可信证据。

05

安装运行

L3 二次确认；最小权限；检查沙箱和出站访问。

06

持续监测

新 CVE、异常调用、降级、SLA、通知与复议。

CI 通过，只能证明检查当时没有发现问题。版本会变，依赖会出现新漏洞，作者凭证也可能被盗。治理必须从作者提交一直管到安装、运行和后续更新；上架后的监测与处置，和入库扫描同样重要。

Governance stack · 三层一起工作

机器守底线，人处理例外，制度保证公平。

LAYER 01

自动门禁

硬性拒绝、分级阈值、签名、SBOM、依赖和静态扫描。

目标：所有插件都守住同一条底线。

LAYER 02

人工复核

L3 深审、动态测试、安全例外和双人确认。

目标：处理机器看不懂的场景、意图和例外。

LAYER 03

处置与申诉

作者行为准则、协议、通知、申辩、决定、复议和安全例外。

目标：每次处置都有依据，也经得起复核。

只靠机器，容易误报，也容易把规则做死；只靠人工，标准会忽高忽低，任务还会越积越多。更稳妥的做法是三层分工：机器守底线，人判断具体场景，正式制度负责通知、申辩和复议。

Trade-offs · 规则也要有边界

门槛要够硬，也要给作者留出迁移和申诉的台阶。

FRICTION

规则太重，作者会流失

L1 尽量少打断；官方仓试运行 2 周再推广；社区仓前 30 天只警告、不阻断。

FALSE POSITIVE

误报怎么处理

每次命中都给原因和文档；支持内联豁免；安全例外至少由 2 名维护者说明业务理由。

MIGRATION

存量插件怎么迁移

新规则先管新提交；存量先扫描并展示结果；严重问题给 90 天修复期。

DUE PROCESS

下架之后怎么申诉

通知 → 申辩 → 决定 → 复议；紧急情况可先下架，但事后必须说明。

CI 预计会从约 3 分钟增至 6–8 分钟，可以靠并行扫描和复用构建产物压缩增量。

来源：飞书提案 §5《实施风险与权衡》嵌入表格。
官方仓先试两周，社区仓前三十天只告警；误报要有原因、有文档、能申请豁免；安全例外至少两名维护者批准；存量严重问题给九十天整改。规则越严，越要提前告诉作者怎么通过、怎么申诉。

Feature spotlight · AI 生成应用

一句话先变成节点计划，再变成可以继续编辑的工作流。

理解需求

先看节点计划

在 UI 里搭建和调试，保留完整的可视化上下文。

日常运行

在 CLI 里运行、观察、组合和批量处理。

自动化把关

在 CI 里触发、回归、审计，并守住发布门槛。

判断依据：Dify 1.15.0 的 difyctl、作用域环境变量、CLI/HTTP 统一错误与可见推理过程。
这不是用 CLI 取代 UI，而是让同一个工作流在不同入口各司其职：设计者在 UI 里搭建，运营和开发在 CLI 里运行，组织再用 CI 做回归和审计。大家使用同一份工作流，不必各自重做一套。
02
Mode two · 正式的人机交接

HITL 不是失败后叫人救场，而是在关键节点把决定交给人。

AGENT

把材料准备好

收拢上下文，给出备选方案，并指出风险。

→
HITL FORM

把问题说清楚

用选项、附件和明确字段，把问题交到人手上。

→
EXPERT

判断和补充

只在关键时点做决定，不必从头返工。

→
WORKFLOW

接着往下跑

带着人的决定继续执行，并把过程留档。

判断依据：Dify 1.15.0 更丰富的 HITL 表单和推理过程留存能力。
更好的分工是：Agent 先把材料备齐，表单把选项和文件送到专家面前，人只在关键处做判断，工作流带着决定继续运行，同时把过程留档。人负责拍板，机器负责把前后工作做完整。
03
Mode three · 可复用的数字角色

Agent 有固定环境、固定做法和名册身份，才真正能复用。

ENV

Linux Sandbox

代码与 shell 在隔离环境中执行，能做什么可以管住。

METHOD

Skills

把 SOP、工具、脚本与知识打包为可分发能力。

IDENTITY

Agent Roster

在工作区内登记、管理、引用和复用 Agent。

COACH

Builder Agent

通过对话配置环境、安装软件、创建 Skills 和文件。

组织要管理的不再只是一段提示词，还包括运行环境和能力包。

判断依据：Dify 1.16.0 Dify Agent (Beta) 的 sandbox、Skills、Agent roster 与 builder agent。
一个角色不再只靠一段提示词来定义。可复用 Agent 还包括 Skills、文件、工具、知识和运行环境。“谁来做”不再是口头安排，而是组织可以登记、复用和审计的一套配置。
Mode four · 跨角色协作协议

工作流开始负责跨角色的交接、状态和证据。

HUMAN

目标与授权

定义结果、边界、预算，以及哪些节点必须人工判断。

AGENT

自主执行

在沙箱里调用 Skills、文件、工具与知识。

WORKFLOW

状态管理

管理顺序、状态、重试、HITL、归档和运行观测。

MCP

对外接口

用结构化输出、版本协商和动态身份接入外部系统。

判断依据：Dify 1.16.0 的 Agent Workflow integration、workflow-as-MCP structured output、dynamic headers 与 run archives。
工作流不只是自动跑步骤。它还要说明：谁在什么时候出手、用什么身份、交付什么格式、留下哪些证据。MCP 让外部系统按这套约定调用，Agent 节点则把自主执行纳入同一条流程。
Target operating model · 四类责任

系统要稳定运行，四类责任必须各有主人。

01 / HUMAN

目标与结果责任

设定目标、批准高风险动作、处理例外，并对业务结果负责。

02 / AGENT

探索与执行

在受控环境中拆解任务、调用 Skills，交出结构化结果。

03 / WORKFLOW

状态与证据

管理顺序、状态、HITL、重试、归档、成本和运行观测。

04 / GOVERNANCE

权限与边界

插件分级、策略即代码、身份、数据流、签名、监测与处置程序。

谁授权、谁管状态、谁对结果负责，都要说得清。

把前后两部分合起来看：人定目标、做决定、对结果负责；Agent 负责探索和执行；工作流负责状态和证据；治理负责权限和边界。这不是组织架构图，而是每个生产系统都必须回答的四类问题。
