01 · 先看插件拿到了什么

装上一个插件，等于放开代码、数据和网络三类权限。

{ }

代码执行

运行依赖、命令和二进制，也能发起模型调用。

↕

数据访问

读取文件、对话、知识库、凭证和工作区上下文。

◎

网络访问

连接第三方 API、任意 URL 和其他外部服务。

治理要回答的不是“能不能装”，而是它能做什么、证据在哪、出了事谁负责。

插件不是一个普通前端组件。它同时获得代码、数据和网络三类能力。所有后续门禁都应从权限出发，而不是从作者身份或功能描述出发。

Risk proportionality · 权限越大，门槛越高

低风险插件快速通过，高风险能力必须增加证据和人工判断。

档位典型行为机器检查人工审核用户感知
L1固定 HTTPS API；不写本地文件基础门禁 + Semgrep 提示20% 抽检不额外打断
L2用户文件 / URL；上传下载与复杂解析中高危依赖阻断；警告需解释轻量人工审查展示数据去向
L3命令、SQL、SSH、浏览器、本地文件、任意 HTTP警告全部阻断；低危以上依赖阻断深度审核 + 动态测试风险提示 + 二次确认

作者自评与机器识别取高值，审核人仍可上调。

来源：飞书提案附录 C《风险分级标准》。
治理不能一刀切。风险档位由权限和数据行为决定，作者自评与机器识别取更高档，人工审核还可以上调。这样低风险贡献者不会承担 L3 成本，高风险能力也不会靠运气上线。

03

04

05

06

新 CVE、异常、SLA、下架与复议。

版本会变，依赖会出现新漏洞，作者凭证也可能被盗。治理必须从提交一直延伸到安装、运行和后续更新；上架后的监测与处置，和入库扫描同样重要。

Three-layer governance · 机器、人、制度各管一层

自动化守底线，人工判断上下文，制度负责处置和申诉。

01 · AUTOMATION

自动门禁

  • 本地预检与 CI 同源
  • 风险识别与证据生成
  • 重复检查零人工成本
目标：一致、快速、可复现
02 · HUMAN REVIEW

人工复核

  • L2/L3 看业务上下文
  • 检查数据用途与最小权限
  • 对例外给出有期限批准
目标：判断机器看不懂的语境
03 · PROCEDURE

处置与申诉

  • 通知、下架、复议与恢复
  • 保留版本、时间戳与负责人
  • 让作者有明确纠错路径
目标：有权力，也有程序
机器适合执行稳定规则，人适合判断上下文，制度则约束平台如何使用下架和阻断权力。三层缺一不可。
Roadmap · P0 / P1 / P2

先堵住明显风险，再把证据做成产品能力。

P0 · 0–30 DAYS

先止血

补全 .difyignore

本地预检 + CI 硬底线

L1/L2/L3 自评与识别

建立下架与例外负责人

输出：最小治理闭环
P1 · 30–90 DAYS

再形成证据

依赖、SAST、SBOM

审核报告与修复定位

作者身份与来源证明

用户侧权限和数据流

输出：可复核的 Trust Center
P2 · 90–365 DAYS

最后持续运营

签名与可复现构建

持续 CVE 与异常监测

分档 SLA 与透明指标

企业策略与市场联动

输出：持续信任系统
路线顺序很重要。P0 先让明显风险进不来；P1 把机器证据变成审核和用户界面；P2 才做签名、持续监测和指标透明。
Adoption design · 规则要硬，迁移要有台阶

治理不能只追求拦得住，还要让作者修得动、存量迁得完。

FRICTION

新作者门槛

模板、示例包和本地预检要默认可用，避免第一次失败发生在远端 CI。

指标：首次通过率
FALSE POSITIVE

误报成本

规则要有可解释原因、最小复现、抑制方式和到期复核。

指标：申诉翻转率
LEGACY

存量迁移

先标记、再限期整改、最后按风险阻断；高风险优先，不要求一夜清零。

指标：高风险清零周期
APPEAL

例外与申诉

批准必须带负责人、范围、理由和过期时间，处置全过程可追溯。

指标：处置 SLA
治理摩擦要被设计，而不是被忽略。首次通过率、误报翻转率、高风险清零周期和处置 SLA，能同时衡量安全和生态体验。
Executive decisions · 三件事需要拍板

没有明确的风险偏好、责任边界和投入顺序，治理会停在提案里。

01 / RISK

哪些能力必须按 L3 管？

命令、SQL、SSH、浏览器、本地文件和任意 HTTP 是否全部进入深度审核与二次确认。

决定风险偏好与默认阻断线
02 / LIABILITY

平台对外承诺到哪里？

审核深度、推荐机制、徽章文案、下架程序和作者协议必须给出一致答案。

法务、产品、市场共同签字
03 / OPERATIONS

谁长期运营这套系统？

扫描规则、人工复核、CVE 响应、申诉和透明指标都需要固定 owner 与预算。

治理是持续运营，不是一次项目
管理层要拍板三件事：风险偏好、责任边界、运营投入。只批准工具采购而不明确这三项，治理最终仍会靠临时协调。

Target operating model · 四类责任

系统要稳定运行，目标、执行、状态和边界必须各有主人。

01 / HUMAN

目标与结果责任

设定目标、批准高风险动作、处理例外，并对业务结果负责。

02 / AGENT

探索与执行

在受控环境中拆解任务、调用 Skills，交出结构化结果。

03 / WORKFLOW

状态与证据

管理顺序、HITL、重试、归档、成本和运行观测。

04 / GOVERNANCE

权限与边界

管理插件分级、身份、数据流、策略、监测与处置程序。

谁授权、谁管状态、谁对结果负责，都要说得清。

人负责目标与结果，Agent 负责探索执行，Workflow 管状态和证据，Governance 管权限和边界。任何生产场景都应把四类责任映射到具体 owner。
