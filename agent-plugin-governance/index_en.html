This story connects two questions: what boundaries and evidence an enterprise needs before accepting open plugins, and how Human, Agent, Workflow, and Governance divide responsibility once Agents reach production. The three releases form a clear progression from entry points, to an Agent system, to production trust.
01 · Start with what a plugin receives

Installing one plugin opens three classes of authority: code, data, and network.

{ }

Code execution

Run dependencies, commands, and binaries, and invoke models.

↕

Data access

Read files, conversations, knowledge, credentials, and workspace context.

◎

Network access

Connect to third-party APIs, arbitrary URLs, and external services.

Governance must answer more than “can it install?” What can it do, where is the evidence, and who owns the outcome?

A plugin is not just another UI component. It receives code, data, and network authority. Every downstream control should follow from those capabilities, not from the author name or marketing description.

Risk proportionality · More authority, more evidence

Low-risk plugins should move quickly; high-risk capabilities require stronger proof and human judgment.

Governance should not be one-size-fits-all. The tier follows permissions and data behavior. This keeps low-risk contributors moving while ensuring high-risk capabilities do not ship on optimism.

Three-layer governance · Machine, human, and procedure

Automation guards the floor, people interpret context, and procedure governs enforcement and appeal.

01 · AUTOMATION

Automated gates

  • One policy for local checks and CI
  • Risk detection and evidence generation
  • Zero marginal cost for repeat checks
Goal: consistent, fast, reproducible
02 · HUMAN REVIEW

Contextual review

  • L2/L3 business context
  • Data purpose and least privilege
  • Time-bounded exception approval
Goal: judge what machines cannot
03 · PROCEDURE

Action and appeal

  • Notice, removal, appeal, restoration
  • Version, timestamp, and owner history
  • A clear correction path for authors
Goal: power constrained by process
Machines execute stable rules, people interpret context, and procedure constrains how the platform uses its blocking and removal authority.

Adoption design · Hard rules need a migration path

Governance must block risk while keeping remediation practical and legacy migration finite.

FRICTION

New-author burden

Templates, samples, and local checks should work by default, before the first remote CI failure.

Metric: first-pass rate
FALSE POSITIVE

Noise cost

Rules need explanations, minimal reproductions, suppressions, and expiry reviews.

Metric: appeal reversal rate
LEGACY

Installed base

Label, remediate by deadline, then block by risk; prioritize high-risk artifacts.

Metric: high-risk burn-down
APPEAL

Exceptions

Every approval records owner, scope, rationale, and expiry, with a traceable action history.

Metric: action SLA
Governance friction should be designed, not ignored. First-pass rate, appeal reversals, high-risk burn-down, and action SLA measure both safety and ecosystem health.
Executive decisions · Three calls to make

Without explicit risk appetite, liability boundaries, and operating ownership, governance stays a proposal.

01 / RISK

Which capabilities are always L3?

Decide whether commands, SQL, SSH, browser, local files, and arbitrary HTTP always require deep review and reconfirmation.

Set the default blocking line
02 / LIABILITY

What does the platform promise?

Review depth, recommendations, badges, removal procedure, and author terms must tell one consistent story.

Product, Legal, and Marketing sign together
03 / OPERATIONS

Who operates the system?

Rules, human review, CVE response, appeals, and transparent metrics need permanent owners and budget.

Governance is an operating function
Leadership must decide risk appetite, responsibility boundaries, and operating investment. Buying scanners without these decisions only shifts coordination elsewhere.

Target operating model · Four kinds of responsibility

Goals, execution, state, and boundaries each need a clear owner.

01 / HUMAN

Goals and outcomes

Set objectives, approve high-risk actions, handle exceptions, and own business results.

02 / AGENT

Exploration and execution

Decompose work and invoke Skills in a controlled environment, returning structured results.

03 / WORKFLOW

State and evidence

Manage order, HITL, retries, archives, cost, and runtime observability.

04 / GOVERNANCE

Authority and boundaries

Manage plugin tiers, identity, data flow, policy, monitoring, and action procedure.

Authorization, state ownership, and outcome accountability must be explicit.

Human owns goals and results, Agent owns bounded execution, Workflow owns state and evidence, and Governance owns authority and boundaries. Every production use case should map these four responsibilities to named owners.
