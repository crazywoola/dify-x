One-line mental model

Workflow owns order. Agent owns judgment. Skill owns method. Stripe owns facts.

Workflow = SOP

Inputs, branches, approval, and outputs stay deterministic.

Agent = colleague

For open-ended work, decide when and how to use capabilities.

Skill = job aid

Package Stripe procedures, scripts, and boundaries once.

Stripe = system of record

The real state of customers, prices, subscriptions, and links.

Demo A · Build Agent

First natural-language input: “hire” a Stripe Billing Operator.

● ● ●AGENTS → CREATE → BUILD MODE
Build a Stripe Billing Operator: 1. Stripe Sandbox only. Read the key from Secret environment variable STRIPE_SECRET_KEY. 2. Create a stripe-billing Skill to look up customer/subscription by email and create Payment Links. 3. Read-only by default. Return proposed_action first; write only when the task contains APPROVED=true. 4. Never refund, cancel, or delete. Never accept or expose card numbers. 5. Return strict JSON: status, action, customer_id, payment_link, object_ids, evidence, error. 6. Use the Stripe Python SDK and create a readable build note.

Dify 1.16.x Build mode can configure prompts, Skills, files, and environment variables through conversation; environment values can be marked Secret. See Build an Agent.

Five guardrails

Grant authority in this order.

01

Sandbox

Prove the process before touching real money.

02

Restricted Key

Credential permits only necessary objects and actions.

03

Action Allowlist

Skill implements only approved capabilities.

04

Human Input

Irreversible or money-moving actions require approval.

05

Evidence

Return IDs, status, errors, and request_id.

Dify notes that the Community Edition Agent runtime is not a hardened security boundary between mutually untrusted workloads. Strict environments need additional hardening. See the New Agent security notice.

16:10–17:25. Production also needs egress controls, secret rotation, evaluations, and alerting. These five are the minimum starting point.
When to use it

Agents are good at judgment. They should not invent financial policy.

Good Agent work

  • Cross-object lookup and synthesis
  • Choose among read-only tools
  • Draft proposed actions and explanations
  • Turn unstructured tickets into structured tasks

Keep deterministic or human

  • Amount math and currency validation
  • Discount, refund, and cancellation policy
  • High-value or irreversible authorization
  • Compliance judgment and exception handling
17:25–18:10. The closer work gets to money and policy, the more deterministic logic and explicit ownership it needs.

Appendix A · FAQ

Three common questions

Must I use Agent Toolkit?

  • No
  • Skill + Stripe SDK works
  • MCP or custom tools also work

Why build Agent first?

  • /create can reference it
  • Test capability independently
  • Reuse across Workflows

Can I switch straight to live?

  • Not from this workshop
  • Review permissions, evals, alerts
  • Grant write scope gradually
