01问题的形状

输出不是一段文本，是一张要在画布上活下来的图。

Workflow DSL 描述节点、连线、变量引用和布局。它最终交给 ReactFlow 渲染、交给运行时执行——模型写错一个字段，画布直接加载失败，或者运行到一半吐出原样的占位符。

SCHEMA

每种节点各有一套结构

LLM、代码、工具、分支、迭代……每种节点的 data 字段都不同，拼错即坏。

EDGES

连线还带句柄

分支节点按 case 出边（true / false），句柄接错，线就悬在画布外。

VARIABLES

变量引用全图寻址

{{#node_id.var#}} 指向别的节点的输出，一处失效，静默变成字面文本。

这决定了整个设计的底线：能交给确定性代码的，绝不交给模型。
3:00–5:00。给开发者建立直觉：这不是「让模型写段 YAML」。三个失败模式都很隐蔽——schema 错了不加载，句柄错了线悬空，变量引用错了运行时静默失效。所以要害不在生成，在生成之后怎么保证正确。
02总体设计

一条四段流水线：模型只回答语义问题。

SSE 流式返回：Planner 完成先推 plan 事件，全部装配完成再推 result。用户在等待时先看到计划，而不是转圈。

04Planner

先出计划，再动手：Planner 只决定「有什么、怎么连」。

P-1 产出一份节点计划 每个节点的类型、id、用途描述、工具绑定；外加边拓扑、start_inputs 和应用模式。
P-2 plan 事件先行 计划一出就推给前端，用户先审阅节点清单，不用等整张图。
P-3 schema 校验 + 一次重试 计划结构不合法（边指向不存在的节点等），带着具体错误提示重问一次，再失败就明确报错。
P-4 模式判定折叠进来 chatflow 还是 workflow 不再单独调用一次模型分类，由 Planner 顺带输出，终端节点类型兜底。
planner_prompts.py · max_tokens 4096计划是唯一的拓扑事实来源
8:30–10:00。Planner 的关键角色：它输出的 plan 是后面所有阶段的拓扑事实来源——Builder 按它分工，Assembler 按它连线。重试是「带错误信息的定向重问」，不是盲目重试。JSON 解析失败的纠正信息用追加 user 消息而不是 system 消息，因为部分供应商会丢弃后置的 system 消息。
05Builder

每个节点，一次专注的调用。

Builder 只写语义配置：提示词、代码、变量、参数、工具绑定，返回 {"config": {...}}。id、坐标、连线、包装字段一概不碰——那些轮不到模型。

PROMPT

按节点类型裁剪

system prompt 只带这个类型的 schema 片段；user prompt 带节点身份、用户指令和完整计划，供跨节点引用。

SCOPE

输出边界收紧

明确禁止输出 id、position、edges、viewport——结构字段全部由装配层补。

REFINE

keep 节点不打模型

增量修改时，计划标记为 keep 的节点直接深拷贝现有配置；update 节点带着旧配置进 prompt，只改指令涉及的部分。

node_builder_prompts.py · get_node_builder_system_prompt(node_type)
10:00–11:30。给开发者的要点：把「一个什么都要写对的大调用」换成「N 个只需写对一小块的小调用」，单个调用的任务窄了，质量和延迟同时改善。refine 的 keep/update 语义是保证增量修改不破坏现有图的关键。
06问题一 · 工作空间装了几百个工具

全塞塞不下，砍前 80 个又砍错：那就动态注入。

旧做法是固定截取安装列表的前 80 个工具进 prompt。装得越多，真正相关的工具越可能不在切片里——模型于是开始编造工具名。

≤ 24 直接注入 工具少就不折腾，完整目录进 prompt，零额外调用。
> 24 Tool Router 路由 一次 256 token 的小调用把指令翻成能力查询；本地按短语命中、词面重叠、模糊匹配确定性打分，每个查询取前 3，全局最多 16 个候选。
PIN 点名的永不丢 指令里写明的 provider/tool、refine 图里已经在用的工具，不受任何上限约束。
TRUST 身份最后统一覆盖 不管模型输出什么，工具的身份字段和参数 schema 都在装配时用服务端目录重写——幻觉参数直接被过滤。
tool_catalogue.py · 路由失败回退旧 80 切片 langgenius/difyPR #40611
11:30–13:30。两层设计值得展开：一，路由调用极便宜（256 token、temperature 0），真正的排序在服务端本地做，确定性、可复现；二，hydration 是信任边界——LLM 只贡献参数绑定，工具身份和 schema 永远以服务端目录为准。这就是「装了什么用什么」的保证。
07问题二 · 图必须能正确展示

模型负责生成，Validator 负责让图在画布上活下来。

生成结果先过一条确定性的修复流水线：可以安全推断的错误就地修掉，修不了的带着错误码失败——绝不把坏图交给画布。

R-1 ID 消毒 node-1 这类带连字符的 id 会让 {{#node-1.var#}} 在运行时静默失效；统一改写 id 并递归同步所有引用。
R-2 变量引用对账 逐一核对引用的源节点是否真的声明了那个输出变量；能唯一推断就改写，起点变量缺失就自动补声明。
R-3 布局与默认值 拓扑排序定 X 轴（320px 步进），分支车道分层；ReactFlow 包装字段、边句柄、去重和边 id 全部由代码补齐。
R-4 fail-closed 结构校验 最后一道闸：MISSING_START、GRAPH_CYCLE、DANGLING_EDGE、UNKNOWN_TOOL 等机器可读错误码，可定位到具体节点。
runner.py · _postprocess_graph / _validate_structure langgenius/difyPR #32130
13:30–15:30。修复和校验的分界是明确的设计决策：只修「可以安全唯一推断」的错误（比如引用错但源节点只有一个输出变量）；有歧义的宁可失败，也不猜。举 ID 消毒的例子最有感染力——运行时变量正则只认字母数字下划线，一个连字符就让整条链路静默失效，这类错误靠提示词永远防不完。

CONCURRENCY

线程池 + fail-fast

ThreadPoolExecutor 按节点数收敛 worker；任何一个节点构建失败，立即取消还在排队的任务，不浪费调用。并发度用环境变量运行时可调。

FIELD NOTE

一个踩过的坑

gevent 部署下忘了 monkey-patch：阻塞的 LLM 调用把唯一的 OS 线程钉死，整个 API 进程冻结。修复是在 __main__ 入口最先打补丁。

WORKFLOW_GENERATOR_NODE_BUILDER_MAX_WORKERS=6 langgenius/difyPR #38975
15:30–17:00。性能收益来自两处：prompt 变小（TTFT 和补全都快），加上关键路径从 N 次串行变成一波并行。fail-fast 语义讲一句：省的不只是时间，还有 token。gevent 的坑对自托管 Dify 的开发者是实用信息。
09与其他自动生成 DSL 的差别

差别不在会不会生成，在生成之后发生什么。

A

产出是能加载的草稿，不是一段文本

多数方案到「输出一份 YAML/JSON」为止；这里结构正确性由确定性装配层保证，产出直接落进画布，能连线、能运行、能继续编辑。

B

工作区感知

只引用你真正安装了的工具；身份与参数 schema 由服务端目录覆盖，不会幻觉出不存在的工具，也不会把工具名拼错。

C

Refine 是增量的

keep / update 分明，保留既有连线、容器关系和分支句柄。改一处不用推倒重来，这是「二次生成」和「持续编辑」的分水岭。

D

失败是可解释的

机器可读错误码定位到节点，前端可以高亮出错位置——而不是一句「生成失败，请重试」。

17:00–19:00。收束到差异化。四点的共同来源就是架构本身：因为有确定性装配层，产出才可加载；因为有路由和 hydration，才有工作区感知；因为 plan 是拓扑事实来源，refine 才能增量；因为 fail-closed，失败才可解释。
Closing

让模型只回答语义问题，
结构、上下文和失败，都交给工程。

上下文按需注入，结果确定性兜底，错误机器可读。这套办法不只属于 Workflow 生成——任何「LLM 产出结构化产物」的系统都用得上。
