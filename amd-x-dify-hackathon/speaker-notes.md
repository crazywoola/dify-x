# AMD × Dify Hackathon｜15 分钟中文演讲稿

> 总时长：15:00
> 建议语速：每分钟约 220–240 字。方括号内是现场动作提示，不需要念出来。

## 01 · 封面（00:00–00:45）

大家好，我是 Banana，来自 Dify Developer Relations。

今天想和大家聊一个很具体的问题：怎样把一句提示词，做成一个能规划、能调用工具、能完成真实任务的私有智能体。

整个方案分成两部分：Dify 负责工作流、知识库、工具和应用界面；AMD Radeon 负责在本地运行模型。接下来我会用一个实际 Demo，把 Dify、Lemonade 和 Radeon 串成一套完整方案。

**转场：** 先用一分钟认识一下 Dify。

## 02 · Dify 开源社区（00:45–01:55）

Dify 是一个开源的智能体应用开发平台。工作流、RAG 知识库、模型和工具接入，都可以在同一个协作空间里完成。应用做好后，既可以使用云服务，也可以部署在自己的服务器或私有网络中。

准备这份演示稿时，Dify 在 GitHub 上已经获得大约十五万 Stars；LFX Insights 记录的贡献者数量是 13,929。数字背后是一个活跃的开源生态：遇到问题可以查代码、看讨论，也能找到插件、示例和其他开发者的实践。

对参赛团队来说，这意味着不用从空白项目开始搭建账号、知识库、工作流和应用界面，可以把更多时间放在真实任务、用户体验和本地模型接入上。

**转场：** 有了平台，下一步先看清 Track 2 怎样评分。

## 03 · Track 2 评分（01:55–03:10）

Track 2 的评分分成两部分。

六十分看功能完整性和应用价值。评委关心的不只是模型能不能说出一段流畅的话，而是智能体能不能理解目标、查询资料、调用工具，并把一项真实任务做完。

另外四十分看 AMD Radeon 和 ROCm。项目至少要说明模型确实在本地运行，并展示基本的运行状态。性能不是今天的主线，所以后面不会展开复杂的测试方法。

准备项目时，建议先选一个值得解决的任务，再把本地推理放进完整流程。评委最终看到的，应该是一个能解决问题的作品，而不是几个互不相连的技术演示。

**转场：** 接下来把 Dify 和 Radeon 的分工放进同一张架构图里。

## 04 · 分工与端到端架构（03:10–04:50）

[沿着图从左向右讲]

流程从用户任务开始。除了问题本身，最好同时明确私有资料、权限范围和验收标准。

任务进入 Dify 后，Workflow 负责理解目标、检索知识、调用工具和核对结果。Dify 是整个流程的总控，但不需要自己承担模型计算。

当流程需要推理时，Dify 通过 OpenAI-compatible API、Tool 节点或 HTTP Request，把请求交给 Radeon 上的本地模型服务。Radeon 和 ROCm 负责执行模型，让敏感数据留在受控环境中。

模型结果回到 Workflow 后，先检查工具执行情况和验收条件。符合要求再交付；信息不足就询问用户；执行失败则调整步骤或安全结束。

这套分工也便于替换组件：更换模型时不用重写整个应用，调整工作流时也不需要改动底层推理服务。

**转场：** 下面分别把编排端和本地模型端启动起来。

## 05 · Dify Docker Quick Start（04:50–06:00）

先看 Dify 社区版。准备好 Docker 和 Docker Compose 后，最低建议是两核 CPU、四 GiB 内存。

如果还没有源码，先克隆 Dify 仓库。进入 `dify/docker` 目录，复制环境变量文件，然后执行 `docker compose up -d`。容器启动后，打开 `localhost/install`，完成管理员账号和基础配置。

这里启动的是应用和工作流服务，不是在容器里直接运行 Radeon 模型。模型推理由后面的 Lemonade 服务提供，再通过插件或接口交给 Dify 调用。

现场不必逐条解释所有 Docker 配置。让观众看到容器正常启动、安装页面可以打开，就足够说明编排端已经就绪。

**转场：** 接下来启动真正运行在 AMD 硬件上的本地模型服务。

## 06 · Lemonade Quick Start（06:00–07:40）

Lemonade 的作用，是把 AMD 硬件上的本地模型封装成标准 API。应用开发者可以专注业务逻辑，不需要在项目里维护底层推理代码。

先运行 `lemonade status`，确认服务和硬件状态。然后用 `lemonade run` 下载并启动模型。页面示例使用 Gemma，并通过 `--llamacpp rocm` 指定 ROCm 后端。

服务启动后，会在 `localhost:13305/api/v1` 提供 OpenAI-compatible 接口。对于支持 OpenAI 接口的应用，通常只要更换 Base URL 和模型名称，就能改为本地推理。

右侧四点可以快速理解 Lemonade：接口是标准的；可以使用 AMD GPU、NPU 或混合模式；模型和上下文留在本机；运行日志能够显示 TTFT、TPS 和 Token 数。日志只用来确认服务状态和本地推理路径，不在这里展开性能测试。

现场至少确认三件事：服务正常、模型能返回结果、请求确实走本地接口。

**转场：** 本地服务已经有了，下一步把它接进 Dify。

## 07 · Dify Lemonade 插件（07:40–09:20）

接入过程分三步。

第一，在 Dify Marketplace 搜索并安装 Lemonade 插件。第二，填写模型类型、模型名称和 Server Endpoint。第三，在 Agent 或 Workflow 的模型节点中选择它。

插件不只支持普通文本生成。根据模型能力，还可以接入视觉、结构化输出、Embedding、Rerank、语音转文字和文字转语音。参赛时不用把每项能力都用上，选择真正服务于任务的两三项即可。

这里有一个常见问题：如果 Dify 运行在 Docker 里，容器中的 `localhost` 指向容器自己，不是宿主机。因此 Server Endpoint 要填写容器能够访问的宿主机地址。连接失败时，先检查这个地址，再检查端口和防火墙。

到这里，Dify 已经可以像调用普通模型一样调用 Lemonade。本地推理、知识库、工具和界面都能进入同一条 Workflow。

**转场：** 配置讲完，下面不再看架构图，直接跑一次实际任务。

## 08 · 实际 Demo：私有文档助手（09:20–11:50）

[切换到 Dify 应用；确认 Lemonade 服务和 Radeon 运行状态已经提前准备好]

这个 Demo 只有一个目标：把内部项目文档整理成一份可以马上执行的任务清单。

[点击页面中的文件链接，快速展示演示资料；回到 Dify 知识库，确认已经导入 `demo-launch-plan-zh.md`]

这份文件进入本地知识库。现场输入的提示词是：找出本周未完成事项，按负责人、截止日期和风险输出；信息不足时标记“待确认”，不要自行补全。

[复制页面上的提示词并点击运行]

Dify 先从知识库检索相关段落，再通过 Lemonade 插件调用 Radeon 上的本地模型。模型返回结果后，Workflow 把内容整理成固定字段，并检查负责人和日期是否齐全。

[等待结果时，短暂展示 Lemonade 终端中的本地请求；随后回到 Dify 输出]

现在看结果。能够直接执行的事项给出负责人和日期；原文缺少的信息明确显示“未提供”或“待确认”，而不是由模型猜一个答案。

[点开一条引用，核对它来自原文]

现场只验收三件事：第一，结果能够回到原文；第二，缺失信息没有被补写；第三，输出已经是一份可执行清单。这样就同时展示了本地推理、RAG、结构化输出和任务价值。

如果网络或模型临时不可用，就保留这页作为讲解底稿，并展示事先保存的同一份输出，不要临时更换演示目标。

**转场：** 刚才是一次具体运行，下一页把它归纳成可复用的完整流程。

## 09 · 完整任务闭环（11:50–13:50）

可靠的智能体不能停在“模型已经回答”这一步。把事情做完，并在出错时妥善处理，才算完整。

刚才的 Demo 正好对应这五步。第一，明确任务、私有资料和验收标准。第二，查询本地知识，决定需要哪些信息。第三，调用 Radeon 上的本地模型完成判断和内容生成。第四，把结果整理成固定字段，并核对来源。第五，根据验收标准决定交付还是补充信息。

参赛项目还应该准备一个异常场景，例如工具超时、资料不足、权限不够，或者结果没有通过校验。系统要能说明原因，重新规划、询问用户，或者安全停止。

现场演示一次这样的完整闭环，比连续展示几次顺利聊天更能说明项目价值。评委看到的是任务怎样开始、怎样执行、怎样结束，而不只是模型最后说了什么。

**转场：** 技术路线和实际运行都看完了，最后邀请大家把自己的项目做出来。
