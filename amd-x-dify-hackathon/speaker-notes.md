# AMD × Dify Hackathon｜15 分钟中文演讲稿

> 总时长：15:00
> 建议语速：每分钟约 220–240 字。方括号内是现场动作提示，不需要念出来。

## 01 · 封面（00:00–00:50）

大家好，我是 Banana，来自 Dify Developer Relations。

今天想和大家聊一个很具体的问题：怎样把一句提示词，做成一个能规划、能调用工具、能完成真实任务的私有智能体。

整个方案分成两部分：Dify 负责工作流、知识库、工具和应用界面；AMD Radeon 负责在本地运行模型。接下来的十五分钟，我会从比赛评分讲起，再带大家看 Dify、Lemonade 和 Radeon 怎样连成一套完整方案。

**转场：** 先用一分钟认识一下 Dify。

## 02 · Dify 开源社区（00:50–02:15）

Dify 是一个开源的智能体应用开发平台。工作流、RAG 知识库、模型和工具接入，都可以在同一个协作空间里完成。应用做好后，既可以使用云服务，也可以部署在自己的服务器或私有网络中。

页面右侧有两个数字。准备这份演示稿时，Dify 在 GitHub 上已经获得大约十五万 Stars；LFX Insights 记录的贡献者数量是 13,929。数字本身不是目的，它说明背后有一个活跃的开源生态：遇到问题可以查代码、看讨论，也能找到插件、示例和其他开发者的实践。

对参赛团队来说，这意味着不必从空白项目开始搭建账号、知识库、工作流和应用界面，可以把更多时间放在真实任务、用户体验和本地模型接入上。

**转场：** 有了平台，下一步先看清 Track 2 怎样评分。

## 03 · Track 2 评分（02:15–03:45）

Track 2 的评分分成两部分。

六十分看功能完整性和应用价值。评委关心的不是模型能不能说出一段流畅的话，而是智能体能不能理解目标、制定计划、查询资料、调用工具、管理必要的记忆，并把一项真实任务做完。

另外四十分看 AMD Radeon 和 ROCm。这里至少要说明模型确实在本地运行，并能展示基本的运行状态。性能不是今天的主线，所以后面不会展开一整套测试方法。

准备项目时，建议先选一个值得解决的任务，再把本地推理放进完整流程。不要先堆技术名词，再临时寻找使用场景。评委最终看到的，应该是一个能解决问题的作品，而不是几个互不相连的技术演示。

**转场：** 接下来把 Dify 和 Radeon 的分工放进同一张架构图里。

## 04 · 分工与端到端架构（03:45–05:45）

[沿着图从左向右讲]

流程从用户任务开始。除了问题本身，最好同时明确私有资料、权限范围和验收标准。信息越清楚，后面的智能体越容易做出稳定判断。

任务进入 Dify 后，Workflow 负责理解目标、制定计划、检索知识、调用工具和核对结果。Dify 是整个流程的总控，但不需要自己承担模型计算。

当流程需要推理时，Dify 通过 OpenAI-compatible API、Tool 节点或 HTTP Request，把请求交给 Radeon 上的本地模型服务。Radeon 和 ROCm 负责执行模型，让敏感数据留在受控环境中。

模型结果回到 Workflow 后，不是立刻显示给用户，而是先检查工具执行情况、来源和验收条件。符合要求再交付；信息不足就询问用户；执行失败则调整步骤或安全结束。

这套分工的好处是清楚。更换模型时，不必重写整个应用；调整工作流时，也不需要改动底层推理服务。评委还能一眼看懂哪些判断发生在 Dify，哪些计算发生在 AMD 硬件上。

**转场：** 下面分别把编排端和本地模型端启动起来。

## 05 · Dify Docker Quick Start（05:45–07:05）

先看 Dify 社区版。准备好 Docker 和 Docker Compose 后，最低建议是两核 CPU、四 GiB 内存。

如果还没有源码，先克隆 Dify 仓库。进入 `dify/docker` 目录，复制环境变量文件，然后执行 `docker compose up -d`。容器启动后，打开 `localhost/install`，完成管理员账号和基础配置。

这里启动的是应用和工作流服务，不是在容器里直接运行 Radeon 模型。模型推理会由后面的 Lemonade 服务提供，再通过插件或接口交给 Dify 调用。

现场演示不必逐条解释所有 Docker 配置。让观众看到命令、容器正常启动，以及安装页面可以打开，就足够说明编排端已经就绪。

**转场：** 接下来启动真正运行在 AMD 硬件上的本地模型服务。

## 06 · Lemonade Quick Start（07:05–09:05）

Lemonade 的作用，是把 AMD 硬件上的本地模型封装成标准 API。这样应用开发者可以专注业务逻辑，不需要在项目里自己维护底层推理代码。

第一步运行 `lemonade status`，确认服务和硬件状态。然后用 `lemonade run` 下载并启动模型。页面示例使用 Gemma，并通过 `--llamacpp rocm` 指定 ROCm 后端。

服务启动后，会在 `localhost:13305/api/v1` 提供 OpenAI-compatible 接口。对于已经支持 OpenAI 接口的应用，通常只要更换 Base URL 和模型名称，就能改为本地推理。

右侧四点可以快速理解 Lemonade：接口是标准的；可以使用 AMD GPU、NPU 或混合模式；模型和上下文留在本机；运行日志能够显示 TTFT、TPS 和 Token 数。这里的性能数据只用来确认服务状态和本地推理路径，不需要在演示中展开复杂的基准测试。

如果现场时间有限，至少展示三件事：服务正常、模型能返回结果、请求确实走本地接口。这样本地模型端就讲清楚了。

**转场：** 本地服务已经有了，下一步把它接进 Dify。

## 07 · Dify Lemonade 插件（09:05–11:15）

接入过程分三步。

第一，在 Dify Marketplace 搜索并安装 Lemonade 插件。第二，填写模型类型、模型名称和 Server Endpoint。第三，在 Agent 或 Workflow 的模型节点中选择它。

插件不只支持普通文本生成。根据模型能力，还可以接入视觉、结构化输出、Embedding、Rerank、语音转文字和文字转语音。参赛时不必把每项能力都用上，选择真正服务于任务的两三项即可。

这里有一个常见问题：如果 Dify 运行在 Docker 里，容器中的 `localhost` 指向容器自己，不是宿主机。因此 Server Endpoint 要填写容器能够访问的宿主机地址。连接失败时，先检查这个地址，再检查端口和防火墙。

到这里，Dify 已经可以像调用普通模型一样调用 Lemonade。本地推理、知识库、工具和界面都能进入同一条 Workflow。

**转场：** 最后再看一遍，怎样把这些能力组织成一个真正完成任务的智能体。

## 08 · 完整任务闭环（11:15–13:45）

可靠的智能体，不能停在“模型已经回答”这一步。回答得不错，只是开始；把事情做完，并在出错时妥善处理，才算完整。

这页把流程分成五步。

第一步，明确用户目标、私有资料、权限和验收标准。第二步，查询本地知识和历史记录，制定下一步计划。第三步，调用 Radeon 上的本地模型完成判断或内容生成。第四步，调用工具执行操作，并核对结果、来源和限制条件。第五步，根据验收标准决定交付还是调整。

这里建议大家特意设计一个异常场景。例如工具超时、资料不足、权限不够，或者结果没有通过校验。系统应该能够说明原因，补充信息、重新规划，或者安全停止。

举个简单例子：如果做的是本地文档分析智能体，用户给出一批内部文件和一个整理目标。Dify 先检索相关内容，Lemonade 在 Radeon 上完成本地推理，Workflow 再生成报告并检查必填字段。如果缺少关键资料，就明确告诉用户缺什么，而不是编一个看似完整的答案。

现场演示一次这样的完整闭环，比连续展示几次顺利聊天更能说明项目价值。评委看到的是任务怎样开始、怎样执行、怎样结束，而不只是模型最后说了什么。
